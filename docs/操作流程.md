# OpenClash 配置与规则的操作流程

VERSION: 1.0 (2026-09-06)
涉及：`MAXLYEN/Openclash-Config`、`MAXLYEN/Openclash-Rule`、GL-BE3600 上的 OpenClash

---

## 0. 先理解三层，后面所有操作都是它的推论

```
   你改的东西                        送达路径                              延迟
   ─────────────────────────────────────────────────────────────────────────
A  cfg/*.ini      →  dist/*.ini  →  subconverter 现拉现转  →  config.yaml
   （策略组/顺序）                   触发点：你点「更新订阅」                  秒级

B  rules/list/*   →  rules/yaml/*  →  jsdelivr / raw CDN  →  内核 provider
   （规则内容）                       触发点：内核按 interval 自己拉         最长 8 小时
```

**关键区别**：ini 的改动是**你主动推给内核**的（更新订阅时重新生成整个 config.yaml）；
规则的改动是**内核自己去拉**的，你无法在路由器上"推"，只能等它拉、或强制让它拉。

规则那条路上还叠了 CDN 缓存，所以是两层延迟：

```
GitHub 仓库  ──①CDN缓存──▶  jsdelivr/raw  ──②interval──▶  内核
```

`--check` 的三列就是在量这两层：**仓库**是源头，**CDN**是中间层，**内核**是终点。

## 1. 改配置（策略组、检索顺序、分组归属）

**在哪改**：`Openclash-Config/cfg/Custom_Clash_V2.ini`

```
1. 本地改 cfg/Custom_Clash_V2.ini，改 VERSION 号
2. 本地自查（可选但推荐）
     python3 scripts/validate_ini.py
3. 提交推送
4. 等 GitHub Actions 绿 —— 它会校验结构、生成 dist/、提交产物
5. 路由器：OpenClash → 配置订阅 → 更新订阅
6. 验证：sh /root/scripts/openclash-verify.sh
```

第 4 步**必须等绿**。dist/ 是订阅转换实际引用的文件，CI 没跑完就更新订阅，拉到的还是上一版。

第 6 步看三段：A 段 provider 数与预期一致、B 段 12 个组的出口全对、C 段 10 个域名命中正确。

改了某个组的默认锚点，记得同步改脚本开头的 `EXPECT_GROUPS` / `EXPECT_DOMAINS`。

---

## 2. 改规则内容（域名、IP 条目）

**在哪改**：`Openclash-Rule/rules/list/*.list` —— 只改 `.list`，`.yaml` 是产物

```
1. 本地改 rules/list/xxx.list
2. 本地自查（可选）
     python3 scripts/build.py      # 重新生成 yaml、修正 header
     python3 scripts/validate.py
3. 提交推送（yaml 可以不提交，CI 会自己生成）
4. 等 GitHub Actions 绿。这一步 CI 做四件事：
     · 规范化 list → 生成 yaml
     · 校验产物
     · 提交产物
     · purge 变动文件的 jsdelivr 缓存   ← 消掉延迟①
     · 通知 Openclash-Config 跑联网校验
5. 确认送达：
     sh /root/scripts/openclash-verify.sh --check xxx_Domain
```

第 5 步的三种结果对应三种处理：

| 结论 | 含义 | 怎么办 |
|---|---|---|
| `✓ 已生效` | 内核条数 = 仓库条数 | 完成 |
| `卡在 CDN` | CDN 还在发旧内容 | 看 CI 的 purge 步骤是否 200；或手动 purge（见 §4） |
| `卡在 interval` | CDN 已最新，内核没到拉取时间 | 等，或强制刷新（见 §5） |

**日常改规则不需要做第 5 步。** 8 小时内自然生效就行。只有在调试、或者改的是急着要生效的规则时才查。

## 3. 清理冗余规则

不是每次改规则都要做，攒一批之后跑一次即可。

```
1. GitHub → Openclash-Rule → Actions → Dedupe rules → Run workflow
2. 【不勾】"写入改动"，先看报告
3. 报告在 job summary 里。关注两个数字：
     · A+B 可安全停用 —— 这些是真冗余，可以放心处理
     · C 异组冲突    —— 脚本不动它，绝大多数是"专属优先、泛类兜底"的预期行为
4. 确认无误后再跑一次，这次勾上"写入改动"
5. 它会自动执行 dedupe --apply → build.py → validate.py → 提交
```

脚本是**可逆**的：ini 顺序变了之后，之前被停用但已不再冗余的规则会自动恢复。
所以重复运行安全，不会积累错误禁用。

停用方式是注释而非删除，前缀 `# [已停用-冗余]`，随时可恢复。

---

## 4. 手动 purge（延迟①）

CI 会自动 purge，只有它失效时才手动：

```
https://purge.jsdelivr.net/gh/MAXLYEN/Openclash-Rule@main/rules/yaml/文件名.yaml
```

浏览器打开即可，返回 JSON 里 `"status": "finished"` 表示完成。

**purge 必须在推送之后。** 它会让 jsdelivr 立即回源，推送之前回源拿到的还是旧内容，等于白刷。

raw 源没有 purge 接口，它自己的缓存约 5 分钟，等即可。

## 5. 强制刷新单个 provider（延迟②）

```sh
curl -i -X PUT -H "Authorization: Bearer <你的secret>" \
  http://127.0.0.1:9090/providers/rules/<规则集名>
```

`<你的secret>` 换成 `/etc/openclash/Xboard.yaml` 里 `secret:` 那行的值；
`<规则集名>` 是不带 `.yaml` 的文件名，例如 `OpenAI_Domain`。

- 返回 **204 No Content** —— 请求已接受
- 返回 **404** —— 该内核版本不支持这个接口

**204 不等于已经更新完。** 已实测该内核返回 204 但条数未立即变化，可能是异步拉取。
正确做法是等一分钟再 `--check` 一次：

- 条数变了 → 异步生效，正常
- 条数没变 → 这次拉取没成功，用兜底方案：重启 OpenClash

重启是最可靠的手段：内核启动时会重新加载所有 provider，凡是本地缓存超过 interval 的都会重拉。

## 6. 排查决策树

**改了 ini，路由器没变化**

```
dist/ 更新了吗？ → 没有：CI 没跑完或失败，去 Actions 看
       ↓ 更新了
更新订阅了吗？   → 没有：只重启不更新订阅，用的还是旧 config.yaml
       ↓ 更新了
sh openclash-verify.sh → 看 A 段 provider 数对不对
```

**改了规则，路由器没变化**

```
sh openclash-verify.sh --check <规则集名>
       ↓
仓库列对吗？ → 不对：改动没推上去，或 CI 没跑完
       ↓ 对
CDN 列 = 仓库列？ → 不等：卡在 CDN，看 CI 的 purge 步骤，或手动 purge
       ↓ 相等
内核列 = 仓库列？ → 不等：卡在 interval，等 / PUT 强制刷新 / 重启
```

**某个域名走错了组**

```
sh openclash-verify.sh   → C 段会显示实际命中的 RuleSet 和分组
       ↓ 命中了不该命中的规则集
说明有更靠前的规则抢先了。查 docs/design-notes.md 第三节的检索顺序，
确认那个规则集是不是排在了不该排的位置，或者它里面有过宽的关键词。
       ↓ 内容问题
去 Openclash-Rule 停用那条过宽规则（前缀 # [已停用-过宽]）
       ↓ 顺序问题
去 Openclash-Config 调整 ruleset 的位置
```

## 7. 两条容易忘的

**修改 ini 之后一定要更新订阅，光重启没用。** 重启只是让内核重新加载现有的
`config.yaml`，而 `config.yaml` 是更新订阅时由 subconverter 生成的。

**规则集的名字在两个仓库里是耦合的。** 改 `rules/list/` 下的文件名，
`Openclash-Config` 的 ini 会静默断链。构建 workflow 末尾会通知对方跑联网校验，
所以断了会在几分钟内变红——但前提是你没把那步的 `DISPATCH_TOKEN` 弄过期。
fine-grained PAT 有有效期，到期后那一步会变黄，留意一下。
